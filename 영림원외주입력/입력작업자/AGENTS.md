# 영림원 입력 작업자 — 어떤 AI든 여기부터 읽는다

이 문서는 특정 AI 전용이 아니다. Claude·ChatGPT·Gemini·RPA·사람 누구든 이 폴더만 읽고 일을 이어받을 수 있게 쓴다.

> 🧾 **영림원 등록은 입력폼 「대기」 자료만 처리한다. 채팅 지시로 내용을 받아 직접 등록하지 않는다.** (2026-11-01 사장님 「내가 이걸 등록폼을 통해서 에이아이가 등록하게 만드는게 목표지 지금 등록하고 싶은걸 말로해서 에이아이가 등록하게 하는일을 하고 있는게 아니야」)
> 할 수 있는 일: 폼 대기 처리 · 화면을 **보기만** 하는 확인 · 사장님이 명시로 시킨 정리. 폼에 단계가 없는 자료(예: 품목 분류 — v25 에서 생길 예정)는 단계가 생겨 사장님이 폼에 넣으신 뒤 대기로 처리한다. 그 전엔 저장하지 않는다.
> (11-01 이 원칙 전에 채팅 지시로 넣은 것: 공정흐름 시험 2건(지움) · 대분류 T수납장 2003015(남아 있음).)

> 🔑 **영림원은 새 탭을 열기 전에 이미 로그인된 탭이 있는지 먼저 찾아 그 탭을 쓴다. 새 탭은 꼭 필요할 때만 열고, 일이 끝나면 닫는다. 로그인 화면이 나오면 사장님께 새로 로그인을 부탁하기 전에 다른 로그인된 탭부터 확인한다.** (2026-11-01 사장님 「로그인했는데 니네가 이런식으로 로그인 해달라고 해서 이미 로그인되어 있는 화면도 세개나 더있다」) — 크롬 새 탭은 로그인이 이어지지 않는다(11-01 세 번 겪음). 사장님이 보고 계신 화면은 건드리지 않는다. 탭을 닫을 때는 저장 안 한 내용이 없는 것만, 사장님이 쓰실 로그인된 탭 하나는 꼭 남긴다.

> ⚡ **화면에 스크립트가 있으면 먼저 스크립트로 넣는다. 없는 화면은 처음 넣을 때 손으로 하고, 끝나면 그 화면 스크립트를 만들어 푸시한다. 화면이 바뀌어 스크립트가 틀리면 고쳐서 푸시한다.** 목록·쓰는 법·한계 = `스크립트/README.md`. (2026-11-01 사장님 「각 입력마다 채우기 스크립트에 대한 정보를 깃에 저장해서 작업자가 확인하고 빠릿하게 작업할 수 있도록 만들어줘」)

> ⚠ **외부 프로그램(영림원 등) 화면에 맞추는 작업은 반드시 실제 작동 화면을 직접 열어 확인한 뒤 한다.** 표는 오른쪽 끝·아래 끝까지 밀어 모든 칸을 보고, 칸 이름은 화면 글자 그대로 옮긴다. 화면에서 못 본 칸·값은 넣지 않고 「확인 못 함」으로 보고한다. 기록·추측·화면 밖 데이터로 칸을 만들지 않는다. (2026-10-31 사장님 지시 「빨리 바꾸고 다음부터 이런작업 할때는 무조건 실제 작동화면 확인하고 하는것을 깃에 남겨 모든작업자가 유념하도록 해줘」 — 워크센터 원가센터·칸 이름 잘못 사례)

## 1. 역할
입력폼 「영림원외주입력」(`../영림원외주입력.html`)에 사람이 넣어 **「대기」** 로 쌓아 둔 자료를
영림원 K-System Ace 에 **화면으로 옮겨 넣는** 입력 작업자다.

- 서버: `https://inghometest.ksystemace.com` — 테스트 회사 **「아이앤지퍼니처(TEST)」**
- 지금 방식: 사장님이 로그인해 둔 크롬에서 화면 입력(Claude 는 Claude in Chrome 사용).
- 매번 똑같이 되는 일은 나중에 `스크립트/` 에 굳힌다.

## 3. 일하는 순서 (한 건마다)
1. **대기 자료 읽기** — 파이어스토어(프로젝트 `vivivic-4b7ef`, 익명 로그인) 컬렉션 `erp_vendors` → `erp_workcenters` → `erp_classes`(폼 v25 분류) → `erp_items` → `erp_materials`(폼 v25 자재) → `erp_processes` → `erp_flows` → `erp_boms` → `erp_itemflows`(폼 v48) → `erp_itemmats`(폼 v57) → `erp_itemwcs`(폼 v55, ⚠ 공정차수 없는 품목은 넣지 말고 오류 — 화면별-요령 500865) → `erp_contracts` 순서. 같은 단계 안에서는 `createdAt` 오름차순. `status` 가 `대기` 인 것만.
   - 앞 단계에 대기·수정대기·오류가 남아 있으면 뒤 단계는 건너뛰고 `agentNote` 에 이유를 적는다(영림원에 이미 있는 자료는 예외).
   - 사장님이 채팅으로 직접 시키신 일(예: T 테스트)은 폼을 거치지 않을 수 있다. 그때도 아래 2~5 를 똑같이 한다.
2. **진행중으로 바꾸기** — 시작하면 `status` = `진행중`.
   - ⚠ 사람이 폼에서 대기·오류 건을 지울 수 있다(v13 「선택 삭제」·「대기·오류 모두 삭제」). 처리 직전(진행중으로 바꾸기 전) 그 문서가 아직 있는지·아직 `대기` 인지 다시 읽어 확인한다 — 없으면 건너뛴다. 진행중·완료 건은 폼에서 안 지워진다.
3. **영림원 입력** — 그 화면 스크립트가 있으면 스크립트로(`스크립트/README.md`), 없으면 `화면별-요령.md` 의 그 화면 요령대로. 먼저 **조회해서 같은 이름이 이미 있는지** 본다. 있으면 새로 만들지 않는다.
4. **저장 전 확인 → 저장 → 조회로 확인**
   - 붙여넣기·입력 뒤 저장하기 전에, **넣은 모든 행의 모든 칸(오른쪽 끝 비고까지)을 화면에서 폼 값과 한 칸씩 대조한다.** 폼에 없는 칸에 값이 들어가 있으면 저장하지 않는다.
   - 저장 뒤 조회로 **다시 한 칸씩 대조**한다(행이 생겼는지만 보지 않는다).
   - 사례(10-31): 워크센터 여러 줄 붙여넣기 때 T이룸 행 「비고」에 다음 줄 첫 글 「T로앤」이 들어간 채 저장됐다. 코드 칸만 보고 비고를 안 봐서 놓쳤다(사장님 말씀 「이런일이 없도록 입력폼 깃에 기록해두고 해당 작업을 할때 확인하도록 해줘」).
5. **상태 바꾸기** — 됐으면 `완료`, 안 됐으면 `오류` + `agentNote` 에 화면에서 본 오류 문구 그대로.
6. **기록** — `작업일지.md` 에 적고, 새로 안 화면 사실은 `화면별-요령.md` 에, 사장님 말씀 중 규칙이 될 것은 `사장님-규칙.md` 에. 커밋·푸시.

### 3-1. 공정흐름유형(`erp_flows`, 폼 v19 — v20 부터 폼 4단계 「공정·공정흐름」)
- 폼 v20: 흐름을 저장할 때 목록에 없던 공정이 `erp_processes` 에 대기로 함께 쌓인다(`name`·`memo`·`inspect:false`). **공정을 먼저 넣고 흐름을 넣는다**(위 순서 그대로).
- 문서 = `name`(공정흐름유형) · `memo`(특이사항) · `rows`[`seq` 공정순서 · `proc` 공정명 · `next` 후속공정순서 · `last` 최종공정여부]. seq·next·last 는 폼이 채운 값 그대로 넣는다(고치지 않는다).
- 넣는 법은 `화면별-요령.md` 「공정흐름유형등록 (500228)」의 「넣는 법(11-01)」: 왼쪽에 이름 → 저장 → 행 번호 더블클릭 → 상세에 `seq\tproc\tnext` 붙여넣기 → last 줄 최종공정여부 체크 → 저장 전 대조 → 저장 → 조회·더블클릭으로 다시 대조.
- `proc` 는 폼의 공정 기록(대기·진행중·완료) 또는 함께 쌓인 새 공정이다(v20). 흐름을 넣을 때 영림원 공정등록에 그 이름이 아직 없으면(공정이 대기·오류로 남음) 넣지 말고 오류 + agentNote.
- 폼 v22 부터 `name` = rows 의 `proc` 를 「-」로 이은 것(예: T재단-T엣지-T보링). 공정 이름에는 「-」가 없다.
- 공정검사여부(상세)는 회색이라 넣지 않는다. 같은 공정이 두 번 나와도 정상(11-01 T중복시험 저장됨).

### 3-2. 불러오기 요청 처리 순서 (`erp_imports`, 폼 v23 — 영림원 → 폼)
사장님 말씀(11-01): 「이렇게 기존정보 불러오는 버튼도 각 입력에 맞게 코드 수정해서 작업할 수 있도록 실제화면 조사할 것 미리 조사해서 입력폼에 적용해줘」 · 「기존 정보란 이알피에 실제 적용된 각 정보를 불러와야 하는거야」.
원천은 **영림원에 실제 저장된 자료**(조회 화면에서 읽은 값)다. 영림원에는 아무것도 저장·삭제하지 않는다.
1. **요청 읽기** — `erp_imports` 에서 `status` 대기인 것을 `createdAt` 순서로(`ylw.imp.pending()`). 문서 = `stepKey`(누른 단계) · `steps`(읽을 단계 키, 4단계는 `processes`·`flows` 둘) · `only`(`all` 전체 / `T` 이름이 T로 시작) · `mode`(`count` 건수만 / `import` 불러오기).
2. **화면 준비** — ⚠ 이미 열린 탭도 **조회를 다시** 한다(열린 탭의 표는 옛 값, 11-04 T조립을 이렇게 놓침). `steps` 마다 그 조회 화면을 열고 조건을 맞춰 화면 「조회」(`화면별-요령.md` 「영림원 → 폼 불러오기용 조회 화면 조사」 표의 조회 조건). 로그인 화면이면 멈추고 「사장님 로그인 필요」.
   - 거래처조회 = 등록일 시작 x 로 비움 · BOM등록조회-모품목기준 = 최초작성일 두 칸 비움 + BOM등록(500145) 화면을 열어 둠 · 나머지는 열면 저절로 조회.
3. **스크립트 실행** — `공통.js` → `불러오기-공통.js` → 그 단계 `*-읽기.js` → `await ylw.imp.run(요청)`. 스크립트가 진행중 → 읽기 → 폼과 비교 → 완료/오류 + `agentNote`(단계마다 「영림원 n건 · 폼에 없음 · 같음 · 다름」과 다른 점 목록) + `result` 를 적는다.
   - `count`: 세기만 한다. 폼 문서는 하나도 안 바뀐다.
   - `import`: **폼에 없는 것만** 넣는다 — `status 완료` · `source 영림원` · `agentNote 「영림원에서 불러옴(MM-DD)」` · `importedAt` · `importId`.
     폼에 같은 열쇠(거래처·워크센터·공정·흐름 = 이름, 품목 = 품번, BOM = 품번+차수, 외주계약 = 외주거래처)가 있으면 **덮어쓰지 않는다**: 같으면 건너뜀, 다르면 그 문서의 `ylwDiff` 칸에만 차이(폼은 「영림원과 다름」 칩으로 보임). 폼 문서의 status·agentNote·다른 칸은 안 건드린다.
     **예외 하나(폼 v53)**: 불러온 흐름(`source` 영림원·완료·수정 중 아님)의 `rows` 칸이 없거나, 비었는데 영림원 상세에 줄이 있으면 `rows` 만 채운다(`agentNote` 도 바뀜). 폼에 값이 없으니 덮어쓰기가 아니다. 공정흐름 읽기는 상세까지 읽는다 — `rows` 가 비면 폼이 「공정 없음」으로 막는다.
   - 화면에 칸이 없어 못 읽는 폼 칸(거래처 국내외구분·법인/개인 · 외주계약 단위·부가세포함여부)은 넣지도 비교하지도 않는다 → agentNote 「못 읽은 것」에 적힌다.
4. **큰 단계** — 품목(1,568개)·BOM(552개, 모품목마다 화면을 열어 20분 넘게)은 사장님이 「건수 먼저 보기」로 센 뒤 고르신다. `import`·`all` 요청이 오면 그대로 하되 시간이 걸린다고 보고한다.
5. **확인·기록** — 폼에서 그 단계 목록에 「영림원」 칩이 붙었는지 본다. `작업일지.md` 에 요청·결과를 적고 푸시한다.

### 3-3. 수정 대기 처리 순서 (`erp_items` `status` 수정대기, 폼 v34 — 영림원에 이미 있는 품목 고치기)
사장님 말씀(11-02): 「그래 그럼 입력폼을 통해서 바꾸는데 이게 이미입력된것을 수정하는거잖아? 그럼 어떻게 입력폼을 통해 할 수 있을까?」 → 「해봐」.
폼 4 품목 목록에서 완료 건의 「수정」으로 고치면 문서가 `status` **수정대기** 가 된다. 새로 만드는 일이 아니다 — **신규를 누르지 않는다.**
- 문서: 칸 값은 이미 **고친 뒤 값**. `edit` = `{changed: 바뀐 칸 키, before: 고치기 전, after: 고친 뒤, at: 요청 시각, prevNote}` · `editLog` = 이력 배열(요청·완료·취소). 품번(`code`)은 폼이 잠가 바뀌지 않는다.
1. **읽기** — 대기 건과 같은 단계 순서로, `status` 수정대기 인 것을 `edit.at` 순서로. 처리 직전 다시 읽어 아직 수정대기인지 본다(사람이 「수정 취소」하면 완료로 돌아가 있다). 시작하면 `status` 진행중(`edit` 는 그대로).
2. **품번으로 조회** — 품목등록(500215)에서 조회 조건 품번에 `code` → 조회 → 그 품목을 연다. 없으면 오류 + agentNote 「품번 없음」.
3. **전 값 확인** — 화면 값이 `edit.before` 와 같은지 본다. 다르면(누가 영림원에서 따로 고침) 고치지 말고 오류 + agentNote 에 영림원 값.
4. **바뀐 칸만** — `edit.changed` 칸만 `edit.after` 값으로 고친다(품명 = `name`, 규격 = `spec` …, `erp-spec.json` items `fieldMap`). 다른 칸·판매단가 표는 손대지 않는다.
5. **저장 전후 대조** — 저장 전에 모든 칸을 문서 값과 한 칸씩 대조 → 저장 → 품목조회에서 품번으로 다시 대조.
6. **완료 + 이력** — `status` 완료 · `agentNote` 「영림원 수정함(MM-DD): 품명」 · `edit` null · `editLog` 끝에 `{at, kind:'완료', changed, before, after, note}` 를 더한다. 실패면 `status` 오류 + agentNote(화면 문구 그대로), `edit` 는 그대로 둔다(폼에 「수정 대기로 되돌리기」·「수정 취소」가 뜬다).
7. **기록** — `작업일지.md`.
- 11-02 처음 해 봄: 품목등록에서 기존 품목 품명을 고쳐 「저장」 → 확인 창·오류 없이 같은 ItemSeq 가 고쳐짐. 요령 = `화면별-요령.md` 「이미 있는 품목 고치기」.
- ⚠ v23 불러오기가 수정대기 중인 품목을 비교하면 「영림원과 다름」(ylwDiff)이 붙을 수 있다 — 아직 영림원이 옛 값이라 그렇다. 수정을 끝낸 뒤 다시 비교한다.

#### 3-3-분류. 분류 수정대기 (`erp_classes` `status` 수정대기, 폼 v40)
사장님 말씀(11-02): 「분류에는 수정 입력 없나」 → 「분류도 수정할 수 있게 합시다」.
고칠 수 있는 칸 = 대분류(`big`)·중분류(`mid`)·소분류(`name`) 이름 · 순서(`sort`) · 사용여부(`use`) · 비고(`memo`). 순서·사용여부·비고는 **소분류 줄**의 값. 품목구분(`kind`)은 잠김.
- **나무라서 한 번만 고친다**: 대·중분류 이름을 고치면 폼이 같은 대·중분류의 다른 분류 문서(big·mid)와 그 분류를 쓰는 품목·자재 문서(small 경로)를 **이미 바꿔 두었다**(editLog 「따라 바뀜」, 상태 그대로, 목록은 `edit.tree`). 영림원에서는 **수정대기 문서 하나만** 처리한다 — 대·중분류는 영림원에 하나뿐이고 품목은 분류를 코드로 물고 있다. 따라 바뀐 문서는 손대지 않는다.
- 같은 단계에서는 **수정대기를 대기보다 먼저** 한다(대기 문서가 이미 새 대·중분류 이름을 쓰고 있을 수 있음).
1. 다시 읽어 아직 수정대기인지 보고 `status` 진행중.
2. 품목대중소분류정의(502365) → 품목구분 `kind` 라디오 → 조회 → **`ylwCode` 「대/중/소」 코드**로 대분류 줄 찾기 → 더블클릭 → 중분류 줄 → 더블클릭 → 소분류 줄. 코드가 없으면 `edit.before` 이름 경로로 찾는다. 없으면 오류 + agentNote 「분류 없음」.
3. 화면 이름·사용여부가 `edit.before`(바뀌지 않은 칸은 문서 값)와 같은지 본다. 다르면 고치지 말고 오류 + agentNote 에 영림원 값.
4. `edit.changed` 칸만 고친다: big → 대분류 표 그 줄 분류명 · mid → 중분류 표 그 줄 분류명 · name → 소분류 표 분류명 · sort/use/memo → 소분류 줄 순서/사용여부/비고. 표마다 저장.
5. 저장 전 그 표 모든 줄 대조(바뀐 칸이 그것 하나인지) → 저장 → 조회·더블클릭으로 **코드가 그대로**이고 이름이 `edit.after` 와 같은지 대조.
6. 완료 + 이력: `status` 완료 · agentNote 「영림원 수정함(MM-DD): 대분류 …」 · `edit` null · `editLog` 끝에 `{at, kind:'완료', changed, before, after, note}`. 실패면 오류(edit 그대로).
7. `작업일지.md` 에 적는다.
- ⚠ **확인 못 함**: 영림원에서 이미 있는 분류명을 고쳐 저장할 수 있는지 · 대·중분류 이름을 고치면 이어 붙인 하위 이름(예 `리빙룸_수납장`)도 따라 바뀌는지. 처음 할 때 화면으로 보고 `화면별-요령.md` 「품목대중소분류정의」에 적는다. (폼은 이어 붙인 하위 이름을 바꾸지 않고 「따로 수정하세요」라고만 안내한다.)

#### 3-3-흐름. 공정 없는 흐름 채우기 (`erp_flows` `status` 수정대기, 폼 v53)
사장님 말씀(11-04): 「이건 명백히 구조상 문제인거잖아」. 영림원에 이름만 있고 상세 공정이 0줄인 흐름(T조립·T포장)은 500272 저장이 막힌다(`화면별-요령.md`). 폼 6단계 「공정 채우기」로 공정을 넣으면 수정대기가 된다.
- 문서: `edit.changed` = `['rows']` · `edit.before.rows` = `[]` · `rows`·`edit.after.rows` = `[{seq,proc,next,last}]`. **`name` 은 안 바뀐다**(품목별 공정흐름이 이 이름을 쓴다). 흐름을 새로 만들지 않는다.
- 공정이 먼저다: 같이 쌓인 `erp_processes` 대기(새 공정, 예 T포장)를 먼저 넣는다(3 순서 그대로). `proc` 가 영림원 공정등록에 없으면 오류 + agentNote.
1. 처리 직전 다시 읽어 아직 수정대기인지 본다 → `status` 진행중.
2. 500228 조회 → `name` 행 **번호 더블클릭** → 상세가 비어 있는지 본다. **줄이 있으면 고치지 말고** 오류 + agentNote 에 영림원 공정(누가 따로 넣음). 그 행이 없으면 오류.
3. `스크립트/공정흐름유형등록-채우기.js` 의 `ylw.flow.fillRows(문서)` → 대조표 모두맞음 → 저장 → 조회 → 다시 더블클릭 → `ylw.flow.verifyRows(문서)`. `fillHeads` 는 쓰지 않는다(머리는 이미 있다).
4. 완료: 3-3 의 6 과 같다 — `status` 완료 · agentNote 「영림원 수정함(MM-DD): 공정」 · `edit` null · `editLog` 끝에 완료. 실패면 오류 + agentNote, `edit` 그대로.
5. 흐름이 완료되면 8단계 그 흐름 드롭다운이 풀린다. 그 흐름으로 오류 난 `erp_itemflows` 는 사람이 폼에서 「대기로 되돌리기」 하거나 상품을 다시 골라 저장한다 — 대기가 되면 그때 넣는다.
- 공정 모름(`rows` 칸이 없는 불러온 흐름) = 폼이 8단계에서 막는다. 불러오기 `import` 요청 한 번이면 `rows` 가 채워진다(3-2). 11-04 기준 저장소 15건은 모두 `rows` 가 있어 **지금 다시 불러올 일은 없다**.
- 사람이 영림원에서 직접 상세를 채운 경우: 불러오기 `import` 가 폼 `rows` 만 채운다(`source` 영림원·완료·`rows` 빈 문서만). 결과는 agentNote 「공정 채움 n」.
- ⚠ 수정대기 중 불러오기를 돌리면 「영림원과 다름」이 붙을 수 있다 — 3-3 과 같다. 끝낸 뒤 다시 비교한다.

## 4. 지켜야 할 규칙
- **비밀번호를 넣지 않는다.** 로그인 화면이 나오면 멈추고 「사장님 로그인 필요」로 보고한다.
- **기존 자료를 고치거나 지우지 않는다.** 새 행만 만든다. 삭제·행삭제·덮어쓰기·업로드는 사장님께 먼저 묻는다. (예외: 폼의 **수정대기** 문서 — 위 3-3·3-3-분류, 그 문서의 바뀐 칸만.)
- **저장 전에 확인한다.** 값이 다르면 저장하지 않는다.
- **사장님 말씀이 우선이다.** 이 문서와 말씀이 다르면 말씀을 따르고, 이 문서를 고친다.
- **시킨 것만 한다.** 시키지 않은 화면·자료는 보기만 하고 보고한다.
- 테스트 자료는 이름 앞에 `T` 를 붙인다(`사장님-규칙.md`).
- 한 단계가 끝나면 관리자가 「다음」을 줄 때까지 멈춘다(시키신 범위 밖으로 나가지 않는다).
- 공개 저장소다. **비밀번호·계정·실제 거래 자료(사업자번호 등)는 깃에 적지 않는다.** 이름·코드·화면 사실만 적는다.
- ⚠ **실제 운영 전에 영림원 → 폼 일괄 불러오기를 해야 한다** — 폼 v23 부터 단계마다 「영림원에서 불러오기」 단추가 있다. 요청이 오면 위 3-2 순서로 처리한다(`../CLAUDE.md` 「실제 운영 전 꼭 할 일」).
- 영림원에 **직접** 넣은 자료(폼을 거치지 않은 것)가 생기면 `작업일지.md` 에 바로 적는다(무엇을·어느 화면에·코드/이름). 불러올 때 맞출 목록이 된다.

## 5. 기록하는 법
- 채팅에만 남은 사실은 다음 작업자가 못 본다. **알아낸 것은 그 자리에서 파일에 적는다.**
- `작업일지.md`: 맨 위에 `## YYYY-MM-DD 한 줄 제목` → 한 일 · 만든 자료(화면·이름·코드 표) · 막힌 점 · 배운 점.
- `화면별-요령.md`: 화면 제목 아래에 사실만. 확인한 날짜를 붙인다. 확인 못 한 것은 「확인 못 함」이라 적는다.
- 낡은 설명은 지우지 말고 고친다(틀린 것은 고치고, 왜 바뀌었는지 일지에 남긴다).
- 커밋 메시지는 무엇을 했는지 한국말 한 줄.
